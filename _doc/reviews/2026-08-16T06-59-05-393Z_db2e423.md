## deploy/harden.sh

- **Bloquant — priorité du drop-in SSH (`98-anssi-hardening.conf`)** : pour la plupart des directives, sshd retient la **première** valeur lue (`sshd_config(5)`), et les fichiers de `sshd_config.d/` sont lus par ordre lexicographique. Sur les images cloud Ubuntu (cible typique), un `50-cloud-init.conf` avec `PasswordAuthentication yes` est fréquent : il primerait silencieusement, rendant **toutes** les directives du drop-in inopérantes — alors que `sshd -t` passe et que le résumé affiche « authentification par mot de passe désactivée ». C'est exactement le cas que le script prétend corriger. Correctif : renommer en `00-anssi-hardening.conf` (ou `10-…`), et après reload vérifier la valeur effective (`sshd -T | grep -iE '^(passwordauthentication|permitrootlogin)'`) et avertir en cas d'écart.
- `systemctl reload ssh … || systemctl reload sshd … || true` : si les deux échouent, l'échec est masqué et le résumé annonce « appliqué » quand même. À tracer dans SKIPPED/MANUAL. Même motif pour `systemd-timesyncd` (« vérifiée active » même si le enable a échoué).
- Section auditd : `-w /var/log/sudo.log` échoue au chargement si le fichier n'existe pas encore (rien ne garantit qu'un sudo journalisé a eu lieu), et `augenrules --load || true` masque l'échec — le ruleset peut ne jamais être chargé. `touch` du fichier avant chargement + remonter l'erreur réglerait les deux.
- Fichier temporaire sudoers à nom prévisible dans `/tmp` : `mktemp` serait plus propre (risque atténué ici par `fs.protected_symlinks` appliqué plus tôt — mineur).
- L'en-tête documente `ADMIN_USER`, `ENABLE_AUDITD`, `HARDEN_TMP_NOEXEC` mais pas `SSH_ALLOW_USERS`, alors que le README renvoie à cet en-tête pour cette option.
