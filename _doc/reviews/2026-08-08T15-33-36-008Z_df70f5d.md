## Revue de code

### web/db/users.ts
- **Sécurité (bloquant)** : `verifyLoginCode` n'a **aucune limitation d'essais** — un code à 6 chiffres (10⁶ possibilités) sans compteur d'échecs ni throttling est brute-forçable par simple POST répété. Pire, `startLogin` est appelable sans limite : un attaquant connaissant un e-mail inscrit peut régénérer indéfiniment une fenêtre de 15 min (en inondant la boîte de la victime). Ajouter un compteur d'échecs avec invalidation du code après N tentatives + rate limiting par e-mail/IP sur les deux endpoints.
- **Bug (bloquant)** : `registerAmbassador` n'est pas transactionnel. Si l'insert `user` échoue (23505 sur email/login), le `house` reste orphelin — et ce foyer fantôme compte dans `existingHouses` : la rue n'est plus « vide », donc le vrai premier inscrit de cette rue ne sera **jamais** ambassadeur. Enrober house+user dans `db.transaction(...)`.
- Course concurrente : deux inscriptions simultanées sur une rue vide voient toutes deux `existingHouses = 0` → deux ambassadeurs. À traiter avec la transaction (verrou sur la rue) ou une contrainte partielle unique en base.
- `verifyLoginCode` : lecture puis mise à jour non atomiques — deux vérifications concurrentes du même code valide passent toutes les deux. Faire l'update conditionnel (`where loginCode = hash` non nul) et vérifier le nombre de lignes.
- Nommage : `registerAmbassador` est trompeur — la fonction inscrit n'importe quel habitant (le 2ᵉ passe aussi par là avec `isAmbassador=false`). `registerInhabitant` / `registerUser` serait plus juste.
- `findUserByEmail` et `findSessionUserById` ignorent `deletedAt` : un compte soft-supprimé pourrait toujours se connecter / rester connecté (au moins un TODO si la suppression n'existe pas encore).

### web/routes/connexion.tsx
- **Énumération de comptes** : « Aucun compte associé à cet e-mail » révèle si une adresse est inscrite — sensible pour cette appli. Préférer une réponse générique (« si un compte existe, un code vient d'être envoyé »).
- Aucun throttle sur la demande de code → spam d'e-mails via Brevo (coût + nuisance) ciblant n'importe quelle adresse inscrite connue.
- L'e-mail transite dans l'URL (`?email=…`, y compris dans le lien du mail) : historique navigateur, logs d'accès. À éviter pour une donnée personnelle.
- UX : le message d'erreur dit « Redemandez un code » mais l'étape code n'offre aucun moyen de le faire (seul « Utiliser un autre e-mail »). Ajouter un bouton « Renvoyer le code ».
- `secure: ctx.url.protocol === "https:"` : derrière un reverse proxy TLS l'URL interne peut être `http:` → cookie sans `Secure` en prod. À sécuriser via conf.
