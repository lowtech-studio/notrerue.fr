## Revue

### web/routes/rejoindre.tsx
- **Énumération de comptes** : « Cet e-mail est déjà inscrit » permet de tester si une adresse est inscrite — ce que le flux `/connexion` vient justement de corriger. La protection est donc contournable via le formulaire d'inscription. Si l'anti-énumération est un objectif assumé, il faut un flux « e-mail d'abord » (vérification avant création) ; sinon, à assumer explicitement.
- Rue orpheline : `findOrCreateStreet` est appelé **avant** et **hors** de la transaction de `registerInhabitant`. Sur 23505 (login/e-mail déjà pris), la rue nouvellement créée reste en base avec zéro foyer (visible dans `/api/rues`). La correction du foyer fantôme ne couvre donc que la moitié du problème d'origine.
- Incohérence mineure au re-rendu : en cas d'erreur de validation précoce (ex. e-mail invalide), `cityId` est conservé mais `cityLabel` reste vide → le champ Ville s'affiche vide alors que l'id caché est toujours valide ; la rue apparaît déverrouillée sans ville visible. Résoudre la ville avant le retour d'erreur (ou réinitialiser `cityId`).
- Si `sendLoginCodeEmail` échoue après création du compte, l'utilisateur obtient une 500 alors que son compte existe (il pourra redemander un code après 60 s via /connexion). Envisager un catch qui redirige vers /connexion.

### web/routes/connexion.tsx
- L'e-mail circule toujours dans l'URL (`?email=…`, y compris dans le lien du mail) : donnée personnelle dans l'historique navigateur et les logs d'accès. Un état temporaire côté serveur (ou cookie signé court) éviterait cela.
- Renvoi throttlé : la redirection avec `sent=1` affiche « vous allez recevoir un code » alors qu'aucun e-mail n'est parti (utilisateur légitime qui clique « Renvoyer » dans les 60 s). Le code précédent reste valide, donc non bloquant, mais le message induit en erreur.

### web/db/users.ts
- `verifyLoginCode` : la mise à jour d'échec n'est pas conditionnée au `loginCode` lu (contrairement au chemin succès). Course rare : un renvoi de code entre la lecture et l'update peut se faire invalider par un `attempts` calculé sur l'ancienne valeur → le nouveau code est annulé à tort. Conditionner l'update sur `eq(user.loginCode, found.loginCode)` aussi ici.
- `startLogin` : check-then-update non atomique → deux requêtes concurrentes passent toutes deux le throttle et envoient deux e-mails. Mineur.

### web/islands/CodeInput.tsx
- Le rendu conditionné par `IS_BROWSER` produit un markup SSR (input simple) différent du premier rendu client (cases) : Preact doit remplacer le nœud à l'hydratation — ça fonctionne en général, mais c'est fragile (perte de focus/valeur, warnings). Le pattern `mounted` via `useEffect` + `useState` est plus sûr.

### Tests (users_test.ts, connexion_test.ts)
- Les codes « faux » codés en dur (`"000000"`, `"999999"`) ont chacun 1/10⁶ de chance d'être le code généré → test flaky très rare. Tirer un faux code garanti différent du vrai.
