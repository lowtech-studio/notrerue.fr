## Revue

### deploy/provision.sh
- Mineur (cohérence) : `backup.sh`, `monitor.sh` et `backup-pre-deploy.sh` n'ont pas de `chown` explicite — ils héritent `root:root` du `cp` en root, contrairement à `migrate.sh` qui a droit à un `chown root:"$APP_USER"` explicite. Or en ré-exécution sur un fichier existant, `cp` **conserve l'appartenance du fichier destination** (il tronque/réécrit, ne recrée pas) : si l'appartenance avait été altérée entre-temps, elle ne serait pas corrigée. Un `install -m 750 -o root -g root ...` uniforme pour les trois scripts root serait plus robuste et cohérent avec le traitement de `migrate.sh`.
- Mineur (nommage) : trois variables (`DEPLOY_USER` ici, `VPS_USER` dans deploy.sh, `ADMIN_USER` dans harden.sh) pour un même compte. Le commentaire l'explique bien, mais un nom partagé réduirait le risque de mauvaise correspondance (la panne en cas d'écart est silencieuse côté sudoers, comme le note le commentaire lui-même).

### deploy/deploy.sh
- À vérifier (hors diff) : `deploy/seed-cities.sh`, cité par le README comme étape post-premier-déploiement. S'il passe par `sudo` via ssh sans terminal (ex. un `sudo -u notrerue bash -c '...'` comme l'ancien migrate inline), il n'est couvert par **aucune** règle du nouveau `90-notrerue-deploy` et échouera sans tty. Si c'est le cas, il lui faut le même traitement que `migrate.sh` (script fixe + règle dédiée) ou une mention dans le README.

### deploy/README.md
- Mineur (architecture) : la procédure manuelle « serveurs déjà provisionnés » duplique la section sudoers de `provision.sh` (règles, chemins, échappement `\:`) — deux sources de vérité qui peuvent dériver lors d'une future évolution des commandes de `deploy.sh`. Le README le signale (« C'est exactement ce que produit... »), mais un renvoi plus prescriptif (« régénérer via provision.sh plutôt que recopier ») limiterait le risque.
