## Revue

### web/db/schema.ts (et migration associée, hors diff)
- La suppression de la valeur `"recommandation"` de l'enum `post_type` est le point le plus risqué du diff : en production, des lignes `post.type = 'recommandation'` existent probablement. Postgres ne permet pas de retirer une valeur d'enum ; la migration doit recréer le type avec un `USING` qui mappe les anciennes lignes vers `'cherche'` (et idem pour l'ajout de `message.readAt`). Sans ça, le déploiement échoue ou casse la lecture des anciennes demandes. À vérifier impérativement avant merge — le diff tronqué ne montre pas le fichier de migration.

### web/db/posts.ts
- `TAP_LABELS` : mapping de libellés UI (boutons + e-mails) placé dans la couche d'accès aux données. Fonctionnellement OK, mais un module `utils/` partagé (comme `utils/theme.ts`) serait plus cohérent avec le découpage du projet.
- `findPostIdsWithMatchingComment` scanne les commentaires de toutes les rues (filtrage rue appliqué ensuite par la requête externe — aucune fuite, c'est correct). Juste une note perf si le volume de commentaires grandit : pas d'index ni de borne sur cette sous-requête.

### web/routes/reponses.ts
- `rawType` est réinjecté tel quel dans l'URL de redirection sans validation, contrairement à `taps.ts` qui passe par `isPostType`. Sans gravité (URLSearchParams encode, `/fil` revalide), mais incohérent entre deux routes jumelles.

### web/routes/messages.tsx
- `markConversationRead` est appelé dans le GET : effet de bord sur GET (assumé et documenté, OK), mais conséquence visible : `state.hasUnreadMessages` est calculé par le middleware *avant* le handler, donc la pastille reste affichée sur le rendu de la conversation qu'on vient de lire — elle ne disparaît qu'au chargement suivant. À assumer consciemment ou à recalculer après le marquage.
