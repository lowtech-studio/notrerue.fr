## web/db/posts.ts
- `computeExpiresAt("months", n)` utilise `setMonth` : piège classique des fins de mois (31 janvier + 1 mois → 3 mars, pas 28 février). Tolérable pour une expiration approximative, mais ça mérite d'être assumé (un commentaire comme pour le DST serait cohérent avec le niveau de doc du fichier).
- Signature : `months` est obligatoire mais ignoré pour `today`/`week`, d'où l'appel étrange `computeExpiresAt("week", 1)` dans `createPost`. Un paramètre optionnel (`months = MIN_POST_DURATION_MONTHS`) lèverait la fausse impression que ce `1` a un sens.
- Filtrage `or(isNull(expiresAt), gt(expiresAt, now))` correct, `now` non injectable (jamais issu de la requête HTTP), rétrocompatibilité des appelants préservée. RAS côté sécurité.

## web/routes/fil.tsx
- Le second groupe de radios réutilise les classes `compose-post__types` / `compose-post__type` : le nom de classe dit « type » mais balise désormais des durées. Un nom neutre (`compose-post__pills` / `__options`) éviterait la confusion.
- Petite incohérence avec le pattern juste au-dessus : `POST_TYPES` dérive de `Object.keys(POST_TYPE_LABELS)`, alors que les durées fixes sont câblées en dur `(["today", "week"] as const)` au lieu de `Object.keys(POST_DURATION_LABELS)`. Dériver éviterait une désynchro si une durée fixe est ajoutée.
- UX mineure : le `<select>` des mois est modifiable sans que le radio « months » soit coché (la valeur est alors silencieusement ignorée côté serveur). Pas un bug, mais un utilisateur peut croire avoir choisi « 4 mois » en publiant en réalité « Cette semaine ».
- Validation POST correcte (whitelist sur la durée, clamp du nombre de mois, re-saisie réaffichée en cas d'erreur), pas de XSS (rendu serveur échappé), pas de code serveur dans un island.
