## deploy/harden.sh

- **Bloquant — priorité du drop-in SSH (`98-anssi-hardening.conf`)** : pour la plupart des directives, sshd retient la **première** valeur lue (`sshd_config(5)` : « the first obtained value will be used »), et les fichiers de `sshd_config.d/` sont lus par ordre lexicographique. Sur les images cloud Ubuntu (cible typique d'un VPS), un `50-cloud-init.conf` contenant `PasswordAuthentication yes` est fréquent : il primerait silencieusement sur le drop-in, et **toutes** les directives du fichier (PermitRootLogin, PasswordAuthentication, MaxAuthTries...) seraient ignorées — alors que `sshd -t` valide la syntaxe sans broncher et que le résumé affiche « durcissement appliqué » / « authentification par mot de passe désactivée ». C'est précisément le scénario (mot de passe encore actif) que le script est censé corriger. Correctif simple : renommer en `00-anssi-hardening.conf` (ou `10-…`), et idéalement vérifier après reload la valeur effective via `sshd -T | grep -i passwordauthentication` et avertir si elle ne correspond pas à l'intention.
- `systemctl reload ssh … || … || true` : si les deux reloads échouent, l'échec est masqué et le résumé annonce quand même « appliqué ». À signaler dans `SUMMARY_MANUAL`/`SUMMARY_SKIPPED` au minimum.
- Section auditd : `-w /var/log/sudo.log` échoue si le fichier n'existe pas encore (rien ne garantit qu'un `sudo` journalisé a déjà eu lieu), et l'échec d'`augenrules --load` est masqué par `|| true` — le ruleset peut donc ne pas être chargé silencieusement. Un `touch /var/log/sudo.log` avant le chargement + remonter l'erreur réglerait les deux.
- Fichier temporaire sudoers à nom prévisible dans `/tmp` (`/tmp/98-anssi-hardening.sudoers`) : `mktemp` serait plus propre (risque atténué ici par `fs.protected_symlinks` appliqué plus tôt, donc mineur).
- L'en-tête du script documente `ADMIN_USER`, `ENABLE_AUDITD`, `HARDEN_TMP_NOEXEC` mais pas `SSH_ALLOW_USERS`, alors que le README renvoie à cet en-tête pour cette option.
