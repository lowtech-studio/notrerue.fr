## Revue

### scripts/ai-review.ts
- `EXCLUDE_PATHSPECS` contient `":!**/*.lock"` mais pas `":!**/package-lock.json"` : le lockfile npm (7000+ lignes) n'est **pas** exclu. Résultat visible dans cette revue même : il a consommé quasiment tout le budget `MAX_DIFF_CHARS` (60 000), le diff du vrai code est tronqué et ne passe plus que via les contenus de fichiers. Ajouter `":!mobile/package-lock.json"` (ou `":!**/package-lock.json"`).

### web/routes/api/v1/join.ts
- Endpoint non authentifié qui déclenche un envoi d'e-mail à une adresse arbitraire à chaque appel : aucun rate limiting visible ici (le backlog ne le mentionne que pour publication/message). Un bot peut spammer des boîtes via des inscriptions fantaisistes — à couvrir, au moins par IP/e-mail, comme probablement déjà prévu côté middleware (à vérifier).
- R38 (jeton anti-CSRF sur POST `routes/api/`) : non applicable si ces routes n'acceptent que le Bearer et jamais le cookie de session — à confirmer côté `_middleware.ts` (si le cookie y est accepté, un POST cross-site forgeable devient possible, même si l'impact sur `/join` reste faible).
- `postJson` côté mobile n'utilise jamais le paramètre `token` (aucun appelant ne le passe) : paramètre mort, à retirer ou à laisser en sachant qu'`authFetch` est le vrai chemin authentifié.

### web/routes/api/v1/join_test.ts
- Les tests « inscription valide » appellent réellement `sendLoginCodeEmail` : ils dépendent du réseau et d'une `BREVO_API_KEY` valide, et enverront de vrais e-mails vers `*.example.invalid` à chaque run. Le test 502 repose aussi sur un appel réel à l'API Brevo avec une clé invalide. Si `email/brevo.ts` n'a pas de court-circuit en test, ces tests sont fragiles/non hermétiques — envisager un stub ou un flag `BREVO_DRY_RUN`.

### mobile/lib/api.ts
- `authFetch` : `...(init.headers ?? {})` ne fonctionne que si `init.headers` est un objet plat ; avec une instance `Headers` ou un tableau de tuples, le spread produit des en-têtes silencieusement incorrects. Inutilisé aujourd'hui, mais à corriger avant le premier vrai appel authentifié (ou typer `init.headers` en `Record<string, string>`).
- Commentaire de `searchStreets` : « pas de ville sélectionnée → tableau vide » — la fonction ne teste pas `cityId` (la garde est dans l'écran). Commentaire trompeur sur où vit la règle.

### mobile/app/index.tsx
- `getToken().then(setToken)` sans `.catch` : si `SecureStore.getItemAsync` rejette (Keychain indisponible, restauration iOS...), l'app reste bloquée sur le spinner sans message. Prévoir un repli (traiter comme « pas de jeton » ou afficher une erreur).
- État `string | null | "loading"` : la sentinelle `"loading"` dans la même union que le jeton est un peu hacky ; un `useState` séparé (`isLoading`) serait plus clair. Mineur.

### mobile/app/(auth)/inscription.tsx
- `CITY_SEARCH_DEBOUNCE_MS` est aussi utilisé pour la recherche de rues : renommer en `SEARCH_DEBOUNCE_MS`.
- Course possible entre réponses de recherche (pas d'`AbortController`) : une réponse lente d'une saisie précédente peut écraser les résultats d'une saisie plus récente. Mineur à ce volume, mais classique.
- Quand la ville change, `streetName` est conservé (seul `streetSelected` est rouvert) : l'habitant peut soumettre une rue de l'ancienne ville. Le serveur la créera à la volée dans la nouvelle ville (`findOrCreateStreet`) — comportement peut-être voulu (rue homonyme), mais à vérifier.

### mobile/app/(auth)/code.tsx
- En cas d'échec de `handleResend`, l'erreur est affichée via `resendMessage` (style `info`) plutôt que `error` (style `danger`) : un échec d'envoi s'affiche comme une information neutre. Mineur.

### mobile/app/(app)/index.tsx
- `handleLogout` ne supprime le jeton que localement : la session reste valide côté serveur. Cohérent avec le statut « placeholder » documenté et l'item backlog « déconnecter toutes mes sessions », mais à ne pas oublier quand un vrai endpoint de logout existera.

### mobile/eas.json
- Profil `development` : `EXPO_PUBLIC_API_URL: http://localhost:8000` — sur un dev client installé sur un appareil physique, `localhost` ne résoudra pas (même piège que celui documenté dans `.env.example`). Le commentaire du README couvre le dev Metro, pas ce profil EAS ; à préciser ou à laisser vide.
